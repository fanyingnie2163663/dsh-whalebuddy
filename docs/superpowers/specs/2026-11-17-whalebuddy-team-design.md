# 鲸群 · 班组设计

- 日期：2026-11-17
- 状态：待你点头
- 前情：2026-11-09《同事》设计（P1a 已上线，三个同事在册）、2026-11-13《花名册》
- 一句话：把「三个各干各的同事」变成「一个能拆活、能验收的班组」。

## 1. 为什么现在

现有三个同事已经证明两件事：各有记忆的同事能在新会话里直接接着干；文件交接（designs/<slug>/BRIEF.md）比口头转述可靠。缺的是：没人拆活、没人在交付前说不、没有一条从「你说要什么」到「东西摆在你面前」的路。

单 AI 顶班（自己干或开子代理）会幻觉、也不符合最初的制作思路——所以这次不是让一个人演六个，是让六个人各自开工。

## 2. 目标

1. 你只跟船长说目标；船长把活拆成工单，指到具体的人。
2. 每个岗位是真同事：自己的预设、记忆、会话。你不开她的会话，她就不干活——这是防幻觉的结构，不是缺陷。
3. 工单、回执、审查单都是文件，能读、能查、能复盘。
4. 审查独立于执行：审不写、不做，只判；船长不能自己放行自己的活。
5. 不改 DSH 本体，全部落在现有插件与数据目录。

## 3. 非目标

- 不做自动驱动别人的会话（P3 再谈，先验证能力）。
- 不做组织架构图 UI、消息总线、任务看板（P2 再说）。
- 不做同事市场、跨机同步。

## 4. 反目标（做到也算失败）

- 船长替所有人写产物——又变回单 AI。
- 审变成橡皮图章：每张都通过、从不打回。
- 工单写成小作文，接单的人还得猜。
- 同事在自己会话里「顺便」干了别人的活，且不说明。

## 5. 约束（技术事实）

- DSH 的 subagent 不带预设：子代理只是「一个拿了 prompt 的通用代理」，不是某位同事。所以派活只能靠人开她的会话 + 文件工单。
- 注入预算约 1200 字：工单只注入 id 与一行标题，正文由她按需读文件。
- 插件只用公开服务，不做跨会话推送。

## 6. 方案（已选 A）

- **A 真同事 + 文件工单（选中）**：每人一个预设、一个记忆目录；活以工单文件在彼此之间流动；你负责开门。
- B 船长开子代理扮演各岗：不选。子代理没有档案、不积累记忆，等于单 AI 换皮，正撞上你说的幻觉问题。
- C 先 B 后升格：不选。子代理跑过的活不留记忆，升格时等于重来。

## 7. 组织

| 角色 | 名字（可改） | 管什么 | 明确不管 |
|---|---|---|---|
| 船长 | 蓝鲸 | 接目标、拆工单、排顺序、汇总交付、对外只一个人说话 | 不写产物，不自己判过 |
| 审 | 弓头 | 读工单 + 回执 + 产物，出审查单（通过/有条件/打回） | 不定风格、不写文案、不改代码 |
| 视频 | 逆戟（已有） | 按 BRIEF 出成片 | 审美定调、配色、文案 |
| 美术 | 一角（已有） | 选题、定调、出 BRIEF 与分镜 | 渲染、配乐、导出 |
| 开发 | 座头 | 写代码、接页面、跑测试 | 定视觉、剪片子 |
| 资料 | 抹香 | 找资料、核事实、给来源 | 做决定、写最终文案 |

汇报线：你 → 船长；船长 → 逆戟/一角/座头/抹香；审 → 你，副本给船长。船长不能改审的结论，只能「提请复核」，并留痕。

## 8. 一个活怎么走

1. 你说目标。
2. 船长拆工单（2–4 张），写进 `_jobs/<id>/`，给你开工顺序。
3. 你按顺序开她们的会话（面板点开，或侧栏选她）。
4. 她读工单 → 干活 → 产物落工作区 → 回执写进 outbox。
5. 审读工单 + 回执 + 产物 → 出审查单：通过 / 有条件通过 / 打回（附具体条目）。
6. 船长汇总：过了就交付，没过就打回重做（同一张工单，不新开）。

一句流程：你说目标 → 船长拆单 → 你开门 → 她干 → 审判 → 船长交。

## 9. 工单

- 位置：~/.dsh/whalebuddy/_jobs/<job-id>/ 一个目录一张单：`ORDER.md`（派单）、`REPORT.md`（回执）、`REVIEW.md`（审查单）。
- 同事不直接写文件：读写都走插件注册的 `job` 工具（见 §17 裁决 3）。
- 字段：id / from / to / 一句话目标 / 交付物与验收标准（可测）/ 期限 / 依赖 / 不要什么。
- 规则：
  - 一张工单一个交付物；拆不动说明还没想清。
  - 验收标准必须能判真假（「看起来高级」不算）。
  - 接单者可以先退回：写回执前先回「这件事不该我做 / 做不了」，理由进 outbox。
  - 工单不进任何人的私有记忆（沿用花名册的规矩）。

## 10. 审查

- **专职审（默认）**：一个只判不做的人，守同一把尺，交付前必过。
- **互审（补充）**：只在交付跨两个岗位时（如片子 + 落地页），由另一岗位的同事看一眼，写进审查单的「另一双眼睛」，不作放行依据。
- 为什么这样分：专职审解决「标准每次一样」，互审解决「作者看不见自己的盲区」。前者必需，后者按需。
- 清单来源：工单的验收标准 + 通用项（能不能用 / 有没有硬伤 / 说没说谎）。

## 11. 注入改动

新增一段「工单」，只列：id · 一行标题 · 状态（待接 / 待审 / 已审 / 打回），最多 5 条，200 字以内。状态由文件推导，不手写（见 §17 裁决 1）。预算 1200 → 1400。
待办（tasks.json）不动：待办是你答应的事，工单是别人派给她的活，语义不同。

## 12. 面板

P1 只读：「班组」页显示谁在、手上几张工单、最近一张回执的时间与结论。
P2 再加「开工」按钮（用她的预设开会话，已有能力）与状态流转。

## 13. 数据布局增量

- `~/.dsh/whalebuddy/_jobs/<job-id>/{ORDER,REPORT,REVIEW}.md`
- `~/.dsh/whalebuddy/_shared/roster.md` 扩写（已有，维持 700 字上限）
- `~/.dsh/whalebuddy/_shared/charter.md` 新增：放行规则、审查规则、称呼；作为独立一段注入（300 字）

## 15. 怎么算成了

拿一件真活走完一圈：船长拆 3 张单 → 三个人各自开工 → 审打回一次 → 改完放行 → 你把东西拿到手。中间不需要你在会话之间当传声筒（除了开门）。

## 16. 裁决（独立审读之后的五个洞）

审读指出五处不能施工的地方，逐条裁决如下；上面各节已按此改过。

**1. 工单状态不手写，由文件推导。** 一张单一个目录 `_jobs/<id>/`：只有 ORDER = 待接；有 REPORT 无 REVIEW = 待审；REVIEW 写通过 = 已审；REVIEW 写打回 = 打回。取消「在做」——它无法知道，就不假装知道。打回不需要新枚举：REVIEW.md 里 `verdict: bounced` 加一条理由，同一个目录就是退回凭证。

**2. 审查不是第二张工单。** ORDER.md 里带 `reviewer:` 字段；REVIEW.md 写在同一目录。弓头的注入只看「有 REPORT、没 REVIEW、reviewer 是我」的活——她不需要读别人的 outbox，船长也不需要当传声筒。面板的「待审」队列就是同一份推导结果。

**3. 同事不直接写文件，走 `job` 工具。** 插件注册一个 `job` 工具：`list` / `read` / `report` / `review`。理由有三：数据在 `~/.dsh/whalebuddy/` 里，多数会话沙箱够不到；路径只有一处，不会各写各的；写记忆类数据要先确认的规矩，被工具的参数校验替代。P1 因此比原估计大一点，这是值得的那一点。

**4. 规则进提示，单独一段。** `charter.md`（放行、审查、回执三条）作为独立段落注入，300 字；花名册维持 700 字上限不动——700 是「宽到没人读」换来的教训。注入总预算 +500 字（工单 200 + 章程 300），约 +250 token。

**5. 小白在队里，岗位写「日常」。** 她可以接「明天提醒我带伞」这类单；store 不新增退休/隐藏概念。七个人就七个目录，不做特例。

## 18. 裁决：会话是临时的，同事靠记忆活着

不维护常驻会话。每张工单唤醒一个新会话，带上她的档案、默契和工单本身，干完写回执就结束——**工作不进入长期记忆，人靠档案延续**。

落地方式：派单时同时登记一条一次性定时会话（harness 的 `schedule`，`target: new`）。已知限制：定时会话继承排单会话的预设，不是同事的预设；所以岗位的身份由「档案 + 工单」承载，预设只决定模型与工具。这条限制要么等 harness 放开 `agentPreset`，要么接受它——先接受，先跑起来。
